## 四、必须遵守的业务规则

1. **供应商重新提交 = 全新一轮**：所有判断只看**当前轮次**（`confirmsOfCurrentRound`），
   历史确认不参与任何判断（谁该确认、是否完成、金额取哪轮、能否编辑/删除）。
   重提时会作废上一轮的 `finance`（核算）与 `comparison`（统结对比）。
2. **多人确认**：工程师环节可指派**任意多人**，**全部确认后**才流转；
   待办只显示还没确认的人；同一人不能重复确认凑人头。
3. **重提后可改派**：本轮尚无人确认时，财务可重新选择工程师；不改派则沿用上一轮。
4. **身份快照**：`settlementExempt`（独立结算）/ `overseasCollect`（海外采集）在**创建单据时**
   按供应商账号角色解析并写到单据上；服务启动时对历史单据回填。账号改角色不会悄悄改写已建单据。
5. **status 唯一来源**：由 `deriveStatus(currentStage, rejected)` 推导，**禁止直接赋值**。
6. **供应商身份按姓名**：`bill.supplierName` ↔ 账号 `userName`（不是登录名、不是 supplierId）。
7. **数据隔离**：纯供应商只能看到自己的单据与项目；统结方（17）按全量只读处理。

## 六、踩过的坑（务必避免）

### 1. ⚠ 直接改数据库会被运行中的服务覆盖

`app_state` 的集合在**服务内存**里是权威副本，每个 HTTP 请求结束都会防抖全量落盘。
**在服务运行时用 SQL 直接改数据库，下一次请求就会用内存里的旧数据覆盖回去。**

- 本次真实案例：给账号加角色 → 库里改成功 → 几分钟后角色"莫名丢失"，审计日志查不到任何修改记录。
- **正确做法**：改完**立即 `systemctl restart data_label`**，让内存从库重新加载；然后用 API 触发几次确认没被覆盖。
- 更稳的做法是走界面/API 改，而不是直接动库。

### 2. shell 转义会把中文写坏

把含中文的 JSON 拼进 SQL（经 ssh / heredoc / 命令替换）时，Unicode 转义的反斜杠会被吃掉，
中文变成 `u5eb7u5c3c...` 字面量（曾因此写坏过 users 集合）。

- **正确做法**：读用 `mysql ... | base64 -w0`，写用
  `UPDATE ... SET data = CONVERT(UNHEX('<hex>') USING utf8mb4)`（纯 ASCII，零转义风险）。
- 改动前先备份：`mysql -N -B data_label -e "SELECT data FROM app_state WHERE name='users'" > /tmp/users-$(date +%F-%H%M%S).json`

### 3. systemd 的 ReadWritePaths 路径必须已存在

配置里加了 `ReadWritePaths=/opt/data_label/archive` 但目录没建，服务会以 `226/NAMESPACE` 起不来。
部署脚本已在安装单元前 `mkdir -p`。

### 4. 文件行尾混用（CRLF/LF）

仓库里前端多为 LF、后端多为 CRLF，个别文件还是混合。**改代码前先检测行尾**，
否则字符串替换会静默失败。含 JS `\n` 转义的替换，建议用编辑器工具而非脚本拼字符串。

### 5. 部署会重启服务

每次 `npm run deploy` 都会重启，触发启动修复（重定位、身份回填、审计归档）。
所以"改完库没重启"极易被覆盖（见坑 1）。

### 6. 浏览器缓存

部署后页面必须**强刷（Ctrl+F5）**。nginx 已对 index.html 设 no-store、带 hash 的 assets 长缓存。

### 7. 部署脚本的构建检查

`npm run deploy` 在构建失败但 `dist/index.html` 存在时会继续（历史遗留），
曾导致把旧前端产物部署上去。改动后请确认输出里的入口 hash 变化。
