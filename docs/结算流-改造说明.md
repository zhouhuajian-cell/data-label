> 来源：业务方提供的结算流程图 + 2026-09-15 口头确认。
> 状态：**已确认**，代码按此改造；未标注"已实现"的条目仍在待做列表中。

## 1. 流程（业务方版本）

```
供应商创建项目（名称 = 供应商名字 + 结算月份）
        ↓
供应商录入信息：
   ① 结算单详情【项目 + 元素量 + 单位 + 单价 + 总金额，及本次结算合计金额】
      （设计好的 EXCEL 固定格式模板，方便复制）
   ② 上传附件（产出明细表）
   ③ 成本中心比例（如 M57、G91 等占比），总值 = 100%
        ↓
工程师（罗桂林 / 彭晓蕾 / 赵晓伟）+ 张海霞 审核确认数据，
        并核对数据明细及成本中心比例
        ↓
张海霞（可添加工程师）确认数据 → 审核通过 → 抄送柏川
        ↓
甲方确认数据
        ↓
柏川提交结算单 → 与供应商提交的结算单金额对比，判断增幅是否超过 3.5%
        ↓
蔡总（蔡家辉）、算法（马成男）确认
        ↓
（信息有误 → 打回修改，可备注修改内容）
```

## 2. 业务规则（业务方确认）

### 2.1 字段口径

| 项 | 结论 |
|---|---|
| 「元素量」 | 就是数量，**但界面/导出/报错文案统一显示为「元素量」** |
| 「单位」 | 明细需要该字段（项目 + 元素量 + 单位 + 单价 + 总金额） |
| 成本中心比例 | **必须合计 100%**；超/欠都不允许保存 |
| 结算合计金额 | 本次结算的合计金额，供应商提交时给出 |

### 2.2 增幅红线（两个层级，均已实现）

- 对比基准：**供应商提交金额**（元素量 × 单价合计 = `bill.totalAmount`）
- 对比对象：**本次结算金额**（财务核算后的应付金额 `finance.payableAmount`）
- 阈值：**3.5%**
- 超过阈值的处理：**推送报警 + 提交不了**

实现位置：`server/lib/` + `server/services/bills.js`
- `MAX_INCREASE_RATE = 0.035`（导出常量）
- `increaseCheck(bill)` → `{ base, finalAmount, ratePercent, exceeded, limitPercent }`
- `confirmBill` 在**财务 / 负责人 / 感知工程师**三个节点提交前都会再校验一次，超限则抛
  `422 INCREASE_LIMIT_EXCEEDED`，同时向 甲方PM / 财务 / 负责人 推送报警（站内 + 飞书）
- `calculateBill` 保存核算结果后若发现超限，也会立即推送一条"待处理"报警（但不阻止保存核算，便于财务调参到阈值内）
- 详情接口返回 `increaseCheck`，供前端提示"超限不可提交"

#### （B）统一结算层：统结方总金额 vs 各供应商确认金额合计（**业务确认的主口径**）

- 第一环节：与**多家供应商**逐家确认数据与金额 → 形成"供应商确认金额合计"
- 柏川（**统一结算方**）提交**一个总金额**
- 系统对比：`统结方提交总金额` vs `Σ 各供应商确认金额`，增幅 > 3.5% → **推送报警且提交不了**
- 实现：`server/services/bills.js`
  - `computeSupplierConfirmedTotal({ period, projectId, supplierIds })` → 合计（按供应商拆分）
  - `checkTotalSubmission(user, { period, submittedTotal, ... })` → 对比 + 超限报警 + `422 INCREASE_LIMIT_EXCEEDED`
  - 接口：`GET /api/finance/settlement/supplier-total`（给统结方录金额时参考）、
    `POST /api/finance/settlement/submit-total`（提交总金额，超限即拦截）

### 2.3 成本中心比例（已实现校验）

- 字段：`bill.costCenters = [{ name, ratio }]`
- 校验：名称非空、比例 0~100、**合计（保留 2 位）必须等于 100**，否则 `422 COST_CENTER_TOTAL_INVALID`
- 已接入创建 / 修改接口，并落库（MySQL `bills_finance.cost_centers` JSON 列）
