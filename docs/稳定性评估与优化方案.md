# 数据协作平台 · 稳定性评估与优化方案

> 评估日期：2026-09-18 · 范围：10.2.248.6 生产环境 + 本仓库架构
> 性质：只读评估，未改任何代码。带 ⚠ 的建议需要小改代码，其余全部是运维/配置层操作。

## 一、总体结论

**现状健康，可以放心跑。** 单机 31GB 内存（服务仅占 52MB）、磁盘 44%、负载 1.0 以下；MySQL 数据量很小（全部业务数据 < 100KB）；备份、限流、资源隔离、开机自启都已配好。当前阶段不存在"会挂"的风险。

真正的风险不在"现在会不会挂"，而在**三个随时间累积的隐患**：数据增长的写放大、备份的同盘单点、故障时的"无人知晓"。下面按优先级列出。

## 二、已做对的部分（保持现状即可）

| 项 | 现状 |
|---|---|
| 进程守护 | systemd `Restart=always`，3 秒拉起 |
| 资源隔离 | CPUWeight=50 / MemoryHigh=800M / MemoryMax=1536M，与数据挖掘互不挤占，OOM 时优先牺牲自己 |
| 数据库 | bills/bill_items 走关系表（DECIMAL(28,10) 保精度 + 索引）；事务写入；durability 全开（sync_binlog=1, flush=1） |
| binlog | ROW 格式，30 天自动过期，当前仅 11MB×6 |

| 连接池 | 每池 5 连接 + keepalive，当前连接数 3，余量巨大 |
| 安全 | CORS 已收敛到本机两个来源；登录限流 120 次/分；scrypt 密码哈希；JWT 8 小时；路由层权限校验 |
| 部署 | 健康检查 + data_mining 隔离确认 + 每日备份 cron 一键安装 |

## 三、风险点与方案

### P0-1 备份只有一份、且和数据库同盘 ⭐ 最值得先做

**现状**：备份落在 `/root/backup`，与 MySQL 数据同一块盘。磁盘损坏 = 数据和备份一起没。附件 `uploads/`（验收数据原件）完全没有备份。

**方案**（纯运维，不动代码）：
1. `backup-db.sh` 末尾追加一步 `rsync`/`scp`，把最新备份推到**另一台机器**（如 10.2.248.34 的一个专用目录）或内网 NAS。即使按"两台机器完全隔离"的约定，只单向拷贝备份文件、不给对方任何反向访问，不影响隔离。
2. 同一脚本里把 `/opt/data_label/uploads` 打包一起备（当前 308KB，一年也大不到哪去）。
3. 每季度做一次**恢复演练**：拿备份在临时库恢复 → 起服务 → 登录核对。没演练过的备份等于没有备份。

**代价**：一个 cron 脚本改动，10 分钟。

### P0-2 故障无人知晓 ⭐ 平台自带飞书，做告警很便宜

**现状**：服务挂了 systemd 会拉起，但如果 MySQL 挂了、磁盘满了、或服务反复重启，没有任何人收到通知。

**方案**（新增脚本，不改现有代码）：加一个 cron，每 5 分钟：
- `curl http://127.0.0.1:3001/api/health`（现有健康端点）
- `systemctl is-active mysql data_label`
- `df -h /` 使用率阈值（如 85%）
- 异常时 curl 飞书 webhook（复用平台已有的飞书配置）发告警；连续正常只报恢复

**代价**：一个 shell 脚本 + 一条 cron。

### P1-1 app_state「整集合 JSON 重写」是唯一的写放大隐患

**现状**：users/projects/notifications/auditLogs 等 15 个集合，每个是 MySQL 里的一行 JSON。任何一次保存（防抖 300ms）都会在**一个事务里全量重写 15 个集合**。其中 `notifications`（36KB）和 `auditLogs`（36KB）只增不减——半年后每次确认结算单都要重写可能好几 MB 的 JSON，启动解析也随之变慢；且单行 JSON 一旦损坏影响整个集合。

**当前无需处理，但给两条护栏**：
1. **不改代码的做法**：在 MySQL 侧加监控（P0-2 脚本顺带查 `CHAR_LENGTH(data)`），notifications/auditLogs 超过 ~5MB 时告警，届时再动。
2. **需要小改代码的（建议排期）**：把 `notifications` 和 `auditLogs` 迁出 app_state，各自建关系表（时间字段建索引），并加"保留 90 天/最新 N 条"的修剪。这是整个平台唯一值得做的结构性优化，其余集合（users/projects 等）增长极慢，留在 JSON 里完全没问题。

### P1-2 MySQL 写失败时的静默降级，重启后数据回退

**现状**：`saveStore` 写 MySQL 失败会回退写本地 `db.json`，但**重启后只读 MySQL**——降级期间写入的数据会丢。另外保存有 300ms 防抖，进程被 OOM kill 时最后 300ms 的写会丢。

**方案**：
- 运维层（可立即做）：P0-2 的告警脚本加上"检测 `/opt/data_label/server/data/db.json` 是否被更新过"——一旦出现且晚于服务启动时间，说明发生过降级，立刻告警人工介入。
- 代码层（建议，小改）：启动时若发现本地 db.json 比 MySQL 新，打印醒目告警（不自动合并，避免踩数据）；saveStore 失败时同步发飞书。

### P1-3 node 重启 = 全站（含静态页）闪断

**现状**：nginx 把所有请求（包括前端静态文件）都反代到 node:3001。重启服务（每次部署都会做）时，页面和接口一起断 2~3 秒。

**方案**（只改 nginx 配置）：`location /assets/` 与 `location = /index.html` 由 nginx 直接读 `/opt/data_label/dist`（`root` 指令），只有 `/api/` 走反代。部署重启时用户最多丢一个未提交的接口请求，页面加载完全不受影响。

### P2（有余力再做）

| 项 | 说明 |
|---|---|
| `supplier_name` 加索引 | bills_finance 现按姓名隔离/查询，但只有旧的 `supplier_id` 索引。表小无感，数据过万后列表查询会全表扫。一条 DDL：`ALTER TABLE bills_finance ADD INDEX idx_supplier_name (supplier_name)`。同时可清理不再使用的 `idx_supplier`（先确认无查询依赖） |
| 合并两个连接池 | store.js 与 finance-db.js 各建了一个 pool（共 10 连接上限）。无风险，纯整洁 |
| 慢查询日志 | 当前关闭。数据量小无所谓；若开启，`long_query_time=1` 即可 |
| journald 上限 | 日志已占 4GB（多数是历史重启记录）。`/etc/systemd/journald.conf` 设 `SystemMaxUse=1G` 并 `systemctl restart systemd-journald`，防years累积 |
| HTTPS | 内网明文 HTTP，密码走明文传输（存储是哈希的）。内网可接受；若要上需解决自签证书告警或内网 CA |
| node 内存上限 | systemd MemoryMax=1536M 已兜底；无需再加 `--max-old-space-size` |

## 四、建议执行顺序

1. **本周**：P0-1 备份异地化 + 附件备份；P0-2 巡检告警脚本（两件事都是纯运维）
2. **本月**：P1-3 nginx 直出静态；P1-2 的告警部分；journald 上限；supplier_name 索引
3. **排期（需写代码）**：notifications/auditLogs 迁出 app_state + 修剪；saveStore 失败告警
4. **每季度**：恢复演练一次
